1. Para qué sirve este manual

Describe la memoria del sistema (las tablas de Notion, sus campos, sus relaciones y su ciclo de estados) y los esquemas JSON con los que la información viaja entre Notion, Make, la IA y Gmail. Es el documento que necesita una persona nueva para operar el flujo sin leer el blueprint.

2. Mapa de tablas y relaciones

DB2 · Búsquedasuna fila por puesto abierto: requisitos, experiencia mínima, skills, reclutador responsable.
⟵ relación "Búsqueda / Candidatos" ⟶
1 búsqueda : N candidatos
DB1 · Candidatos (CVs)una fila por postulante: datos del CV, estado del pipeline, resultado de la IA, aprobación humana, hilo de Gmail.
DB3 · Base de conocimientocriterios, tono y políticas de la empresa. Se recupera por búsqueda (RAG) y se inyecta en el prompt.
⟵ relación "Búsqueda" ⟶
DB3 → DB2 (opcional)
DB4 · Registro de ejecucionesuna fila por paso ejecutado (OK o Error). Alimenta la tasa de errores del dashboard.
relación "Candidato / Ejecuciones" con DB1

Los datos de la búsqueda llegan a la ficha del candidato por rollups (Puesto, Requisitos, Skills clave, Exp. mínima, Reclutador). Así el flujo de Make lee todo desde un solo bundle (el de DB1) y no hay valores fijos en ningún módulo: cambiar el reclutador o los requisitos en DB2 cambia el comportamiento del flujo sin tocar Make.

3. Esquema de cada tabla

La columna ID es el identificador de la propiedad en la API de Notion; Make lo usa como clave en los módulos Update a Database Item y Create a Database Item. Los IDs fueron fijados al crear la estructura para que el blueprint sea estable.

4. Ciclo de estados de una ficha

RechazadoNotificado vacío y Correo cargadoCEmail de cierre al candidatoRechazado (Notificado ✓)

Contactado—ningunaFin del pipeline automático; el resto es humano—
Anti-bucle. Cada ruta termina cambiando el Estado (o marcando Notificado). Como los filtros del Router exigen el estado anterior, la misma ficha no vuelve a entrar por la misma ruta aunque el trigger la detecte editada. Un ítem editado por Make consume como máximo 2 operaciones (trigger + router) sin efectos.

5. Esquemas JSON de transferencia

Los siete mensajes que circulan por el sistema, en el orden del flujo. Los valores son de ejemplo; los IDs largos están acortados.

5.1 Bundle del trigger — Notion → Make (Watch Database Items)

Make entrega cada ficha editada como un bundle. Los campos de texto llegan como arreglos de rich_text (por eso el flujo usa join(map(…; "plain_text"); "")), los selects como objeto con name, los números y checkboxes como valores simples y los rollups con la estructura de la API de Notion.

{
  "id": "3b4151a7-f4b6-81ab-…",
  "url": "https://www.notion.so/3b4151a7f4b681ab…",
  "last_edited_time": "2026-09-16T14:05:00.000Z",
  "properties_value": {
    "Nombre": [{ "plain_text": "Lucía" }],
    "Apellido": [{ "plain_text": "Fernández" }],
    "Cargo": [{ "plain_text": "Backend Developer" }],
    "Experiencia (años)": 5,
    "Correo electrónico": "lucia@ejemplo.com",
    "Estado": { "name": "Pendiente", "color": "yellow" },
    "Búsqueda": [{ "id": "…id de la búsqueda…" }],
    "Resumen del CV": [{ "plain_text": "5 años en Node.js, APIs REST, PostgreSQL…" }],
    "Puesto": { "type": "array", "array": [{ "type": "title", "title": [{ "plain_text": "Desarrollador Backend Node.js" }] }] },
    "Exp. mínima": { "type": "number", "number": 3 },
    "Reclutador": { "type": "array", "array": [{ "type": "email", "email": "reclutador@empresa.com" }] },
    "Aprobado": false,
    "Notificado": false
  }
}

5.2 Filtro del Router — decide la ruta (tipos correctos)

Los filtros comparan texto con texto (text:equal), booleanos con booleanos (boolean:equal) y usan exist / notexist para detectar datos faltantes. Ejemplo de la ruta A:

{
  "name": "A · Pendiente + datos completos",
  "conditions": [[
    { "a": "{{1.properties_value.Estado.name}}", "b": "Pendiente", "o": "text:equal" },
    { "a": "{{join(map(1.properties_value.`Resumen del CV`; \"plain_text\"); \"\")}}", "o": "exist" },
    { "a": "{{1.properties_value.`Correo electrónico`}}", "o": "exist" },
    { "a": "{{1.properties_value.Búsqueda[].id}}", "o": "exist" }
  ]]
}

5.3 Recuperación de contexto — Make → Notion (Search Objects sobre DB3)

Se piden las entradas cuyo Tema es el puesto de la búsqueda o "General" (máximo 10). El Text Aggregator las une en un solo texto que va al prompt.

{
  "filter": { "or": [
    { "property": "Tema", "title": { "equals": "Desarrollador Backend Node.js" } },
    { "property": "Tema", "title": { "equals": "General" } } ] },
  "page_size": 10
}

5.4 Llamada a la IA — Make → Groq API (Create a Chat Completion)

Prompt de sistema con el contrato de salida; prompt de usuario con la búsqueda, el candidato y el contexto RAG. Salida forzada a JSON y máximo 2.000 tokens.

{
  "model": "openai/gpt-oss-120b",
  "messages": [
    { "role": "system", "content": "Sos un analista senior de selección de personal… Respondé ÚNICAMENTE con un objeto JSON válido…" },
    { "role": "user", "content": "## Búsqueda\nPuesto: Desarrollador Backend Node.js\nRequisitos: …\n## Candidato\nNombre: Lucía Fernández\n…\n## Base de conocimiento de la empresa\n### Criterios · General\n…" }
  ],
  "max_tokens": 2000,
  "temperature": 0.2,
  "response_format": { "type": "json_object" }
}

5.6 Aviso HITL — Make → Gmail (Send an Email) y el Thread ID

El aviso al reclutador lleva un Message-ID propio, derivado del ID de la ficha. La salida del módulo devuelve el threadId, que se guarda en la ficha (campo Hilo Gmail). Cuando el candidato es contactado, el flujo responde al reclutador en ese mismo hilo con In-Reply-To y References, sin crear correos huérfanos.

// entrada
{ "to": ["reclutador@empresa.com"],
  "subject": "[Revisión IA] Lucía Fernández · Desarrollador Backend Node.js · Apto (82/100)",
  "bodyType": "rawHtml",
  "emailHeaders": [{ "key": "Message-ID", "value": "<cand-3b4151a7-f4b6-81ab-…@clasificador-cvs.make>" }],
  "content": "<div>Revisión de candidato… <a href='{{1.url}}'>Abrir la ficha en Notion</a>…</div>" }
// salida
{ "id": "18f3a2c9e4b1d7a0", "threadId": "18f3a2c9e4b1d7a0", "labelIds": ["SENT"] }
// respuesta en el hilo (ruta B, módulo 13)
{ "subject": "Re: [Revisión IA] Lucía Fernández · Desarrollador Backend Node.js · Apto (82/100)",
  "emailHeaders": [{ "key": "In-Reply-To", "value": "<cand-…@clasificador-cvs.make>" },
                   { "key": "References",  "value": "<cand-…@clasificador-cvs.make>" }] }

Make traduce las claves (IDs de propiedad) al formato de la API de Notion. Así queda la ficha después de la ruta A y el registro que se crea en el log:

{ "properties": {

    "Puntaje IA": { "number": 82 },
    "Justificación IA": { "rich_text": [{ "text": { "content": "5 años con Node.js…" } }] },
    "Requisitos faltantes": { "rich_text": [{ "text": { "content": "AWS" } }] },
    "Borrador de respuesta": { "rich_text": [{ "text": { "content": "Hola Lucía…" } }] },
    "Estado": { "status": { "name": "En revisión" } },
    "Hilo Gmail": { "rich_text": [{ "text": { "content": "18f3a2c9e4b1d7a0" } }] },
    "Última ejecución": { "date": { "start": "2026-09-16T14:06:12.000Z" } },
    "Error": { "rich_text": [] } } }

// POST /v1/pages  (registro en DB4)
{ "parent": { "database_id": "…DB4…" },
  "properties": {
    "Ejecución": { "title": [{ "text": { "content": "16/09 11:06 · Clasificación IA · Lucía Fernández" } }] },
    "Candidato": { "relation": [{ "id": "3b4151a7-f4b6-81ab-…" }] },

    "Resultado": { "select": { "name": "OK" } },

En un error, el handler crea el mismo registro con "Resultado": "Error", "Error": true y el mensaje de la API en Detalle, y deja la ficha con "Estado": "Error" y el texto en el campo Error.

6. Operación diaria

Abrir una búsquedaEn DB2 crear la fila con Puesto, Requisitos, Experiencia mínima, Skills clave y el email del Reclutador. Si el puesto tiene criterios propios, agregar en DB3 entradas con Tema = nombre exacto del puesto.
Cargar un candidatoEn DB1: Nombre, Apellido, Cargo, Experiencia (número), Correo, Búsqueda (relación) y Resumen del CV. Estado = Pendiente. En menos de 60 minutos la ficha pasa a "En revisión" y llega el email de revisión.
Aprobar o rechazarLeer el email, abrir la ficha, editar el Borrador de respuesta si hace falta y marcar Aprobado ✓ (envía la invitación) o poner Estado = Rechazado (envía el cierre). El sistema nunca escribe al candidato sin ese clic.
Si una ficha queda en ErrorLeer el campo Error (qué falta o qué API falló). Corregir y volver a poner Estado = Pendiente. Los errores de API se reintentan solos 3 veces cada 15 minutos antes de necesitar intervención.

Qué mirar en el dashboard

  • Tasa de errores (DB4, % de filas con Error ✓): objetivo < 10 %. Si sube, revisar el detalle de las últimas filas: suele ser cuota de Groq/Gmail o fichas incompletas.
  • Fichas en "En revisión": son las que esperan al humano. Si se acumulan, el cuello de botella es la revisión, no el flujo.
  • Tokens por ejecución: si crece, revisar el largo de los resúmenes de CV o de las entradas de DB3.

Convenciones

  • Todos los módulos de Make tienen nombre propio (número + acción) y toman sus valores del bundle: no hay emails, nombres de puesto ni IDs de páginas escritos a mano.
  • Los IDs de propiedad son fijos: renombrar una propiedad en Notion no rompe el flujo; borrarla y crearla de nuevo sí.
  • El blueprint exportado (blueprint/clasificador-cvs.blueprint.json) no contiene credenciales, solo referencias a las conexiones de Make.
